## F-01 — PWA manifest screenshots 404 (console error on every page)

- **Severity:** S3 (minor — no user-facing break, but errors the console on every route and blocks a clean PWA install experience)
- **Area:** PWA / `public/manifest.json`
- **Viewport:** both
- **Repro:**
  1. Log in, land on `/home` (or any route).
  2. Open DevTools Console.
  3. Observe: `Manifest: Line: 1, column: 1, Syntax error.`
- **Root cause (verified):** `manifest.json` is valid JSON (no BOM, parses fine). The error is Chrome's generic manifest complaint triggered because the two referenced `screenshots` entries return **404**:
  - `/screenshots/home-wide.png` → 404
  - `/screenshots/home-narrow.png` → 404
  - (Icons `/icon-192x192.png` and `/icon-512x512.png` return 200 — those are fine.)
- **Fix context:** Either (a) add the two missing screenshot PNGs under `public/screenshots/` at the sizes the manifest declares, or (b) remove the `screenshots` block from `public/manifest.json`. This is roadmap item **P1 #22**. Files: `public/manifest.json`, `public/screenshots/`.

## F-03 — Inline profile fields don't commit on Tab/blur (keyboard users get stuck)

- **Severity:** S2 (major — keyboard-only users cannot reliably save profile edits; the interaction silently drops their input)
- **Area:** Profile edit — `src/app/profile/components/InlineEditField.tsx`
- **Viewport:** both
- **Repro:**
  1. `/profile` → click **Phone Number** (or Personal Email / Ethnicity / DOB) to enter edit mode.
  2. Type a value, then press **Tab** (or otherwise blur via keyboard).
  3. Observe: focus leaves, but the value is **not committed** — `onChange` never fires, the form never becomes dirty, the FloatingSaveBar never appears, and the field stays stuck in edit mode. On reload the typed value is gone.
  4. Contrast: pressing **Enter** or **clicking outside with the mouse** *does* commit.
- **Root cause (code-verified):** `InlineEditField` commits only via (a) `handleKeyDown` on `Enter`, and (b) a `document.addEventListener('mousedown', handleClickOutside)` listener. There is **no `onBlur` handler on the `<Input>`**, so keyboard `Tab`-away neither commits nor cancels — it just moves focus while `isEditing` stays true. (`InlineEditField.tsx:86-118` click-outside is mouse-only; `:143-149` keydown handles only Enter/Escape.)
- **Impact:** Fails keyboard accessibility (WCAG focus/operability). Also a general UX trap: a mouse user who clicks the browser chrome / another app also won't commit. Interacts with the convention use case where people may tab through quickly on mobile keyboards.
- **Fix context:** Add an `onBlur` handler to the `<Input>` in `InlineEditField` that runs the same validate-then-commit logic as `handleConfirm` (guard against double-commit with the click-outside path; a `relatedTarget`/`setTimeout(0)` check avoids committing when focus moves to an internal confirm button). Consider committing on `Tab` explicitly. Add a test.

## F-04 — Profile form has unlabeled inputs (accessibility)

- **Severity:** S3
- **Area:** Profile edit form (surfaced by Chrome/Next a11y audit)
- **Repro:** On `/profile`, DevTools reports two issues: `No label associated with a form field (count: 16)` and `A form field element should have an id or name attribute (count: 4)`.
- **Root cause:** `InlineEditField` renders a shadcn `<Label>` but does not wire it to the `<Input>` via `htmlFor`/`id` (no `id`/`name` on the input). The month/year `<select>`s and skill chip `<button>`s likely contribute to the count too.
- **Fix context:** Give each `InlineEditField` input a stable `id` (derive from `label`) and set `<Label htmlFor={id}>`. Add `name` to the month/year selects. Re-run the audit until the counts hit 0. Ties into roadmap **P2 #24 (accessibility pass)**. File: `InlineEditField.tsx` (+ role/project section selects).

## F-05 — Role/Project start dates accept future dates while "Current"/"ongoing"

- **Severity:** S3 (data-integrity / logical-consistency)
- **Area:** Profile — `YMRolesSection` / `YMProjectsSection` month-year selects
- **Viewport:** both
- **Repro:** On `/profile`, the seeded test data shows **"Sub-Regional Secretary General — Current — Mar 2030 – Present"** and **"convention — Current — Mar 2029 – Present"**. The month/year dropdowns expose future years, so a user can mark a role they "currently hold" as starting in 2030 (today: 2026-07). A current role cannot start in the future.
- **Contrast:** DOB uses a bounded Calendar (`fromYear=1940 toYear=currentYear-10`) and is correctly constrained — the role/project selects are not.
- **Fix context:** Constrain the start month/year selects so that when "I currently hold this role"/"ongoing" is checked, the start date must be ≤ today; cap the selectable year at the current year (or validate on save in `useProfileForm`/`saveProfile`). Also add an end-date ≥ start-date check for non-current entries. Files: `src/app/profile/components/YMRolesSection.tsx`, `YMProjectsSection.tsx`, `hooks/useProfileForm.ts`.

## F-08 — Finance Jotform uses a fixed oversized iframe height (mobile)

- **Severity:** S3
- **Area:** `/finance` — Jotform embed
- **Viewport:** mobile (393px)
- **Repro:** At 393px, the Jotform iframe (`form.jotform.com/233184710128148`) renders at a **fixed 2,781px height** (page scrollHeight 3,364px). Width (361px) fits with no horizontal scroll, but the height is a hardcoded tall value, not auto-sized to the form's actual content.
- **Impact:** Depending on the live form length this leaves a large dead scroll gap or clips the end. Fragile as the form changes. Matches roadmap **P1 #19**.
- **Fix context:** Use Jotform's iframe auto-resize script (`postMessage` height events) or a responsive aspect strategy instead of a fixed height. File: the finance page's Jotform embed component.

## F-10 — Duplicate identical Supabase query on People load

- **Severity:** S4 (minor efficiency)
- **Area:** People page / auth-id resolution
- **Repro:** Loading `/people` fires `GET /rest/v1/users?select=id&auth_id=eq.<uid>` **twice** identically (network trace reqid 456 & 457) in the same load.
- **Fix context:** De-dupe the `auth_id → user id` lookup (memoize / single source, e.g. shared in a context or React cache) so it runs once per load. Low impact (select id only) but easy win. Investigate the two callers (likely middleware self-heal + a client hook both resolving the same id).
