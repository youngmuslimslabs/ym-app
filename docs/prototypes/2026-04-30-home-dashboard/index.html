Home dashboard prototypes

Three layout variants for /home within the existing design system. Greeting (Q1a — Assalamu alaykum), top-aligned layout (Q4b), and varying levels of content density. All cards, colors, type, spacing use the actual globals.css tokens — including --card: 0.99 0 0 from this session's surface-depth commit.

Variant 0 — Reference

Current production home page

What's live today: centered layout, max-w-2xl, just two sections. The audit's "less content than most 404 pages" critique applies here.

This is the baseline — every other variant is a delta on this. Note how vertical centering with so few elements creates a "loading screen" feel rather than a "destination" feel.

Variant A — Stats added

Greeting + current cards + new QuickStatsCard

Adds a personal greeting at the top and a 3-stat band at the bottom. PersonalContextCard and QuickActionCards remain at current size. Top-aligned layout.

Tradeoff: Real data without a feature lift — the stats are aggregate counts, ~3 trivial Supabase queries. Greeting + stats give the page two anchor moments (top and bottom) so the action cards stop feeling like the entire page.

Variant B — Prominent, no stats

Greeting + bigger PersonalContextCard + bigger QuickActionCards

Bigger versions of the existing two sections. PersonalContextCard heading bumps from text-2xl to text-3xl with more padding. QuickActionCards get larger icons (24→28) and more padding. No new stats section.

Tradeoff: Cheapest scope (one CSS-only commit). Doesn't fully resolve "less content than 404" because there's still only navigation + identity. But the prominence shift makes the page feel like a destination, not a placeholder.

Variant D — Editorial

Same content as A — without card chrome, plus conference attendance

Greeting + identity + actions + stats — same four sections, but card surfaces removed. Hierarchy is built from typography size, weight, tracking, and spacing. Quick actions become a typographic list with a refined hover state. Stats become an inline numerical strip. One sharp cobalt accent on the user's name; everything else is grayscale. If the user is registered as an attendee for an upcoming or active conference, a conference section sits between the greeting and the hairline rule — the most prominent slot on the page after the welcome itself.

Tradeoffs: The most "smooth and slick" answer, and the most editorial in feel — closer to Linear / Apple internal tools than a SaaS dashboard. Requires more typographic discipline since every line of text is doing real work without a card to hide behind. The card-less hover state on quick actions does the same job a card hover does today. Conference section is conditional — it disappears entirely when no attendance row exists for the current user. Copy is intentionally minimal (name + date range + action) — the live-vs-upcoming distinction is conveyed by the dot's pulse animation, not by language. Adaptive copy ("Day N of M", session counts, etc.) can come later when the conferences feature has real signal data to drive it.

How to evaluate

  • First-glance reaction — does the page feel like a destination or a navigation index?
  • A vs D is the real fork — same content, but A wraps it in cards while D strips card chrome and lets typography do the work. Which feels smoother?
  • D's quick-action hover state (subtle accent tint, arrow fade-in, icon shifts to primary) — does it feel as good as a card hover? It's the load-bearing interaction in D.
  • Does Geist alone carry D's editorial feel? If D looks "too plain" or "too Linear-clone," that's a signal that typography pairing (Q5) might need to happen before D ships.
  • Imagine this on mobile (375px wide) — D's three-column stats strip will need to stack; A's cards survive better at narrow widths.

Implementation cost (rough)

  • Variant A: ~4 commits — greeting component, QuickStatsCard component, count queries in fetchUserContext, layout switch from centered to top-aligned.
  • Variant B: ~2 commits — greeting component, padding/size bumps to PersonalContextCard and QuickActionCard, layout switch.
  • Variant C: ~5 commits — A + B combined.
  • Variant D: ~5 commits — greeting component, redesigned QuickActionList replacing QuickActionCard, inline StatsStrip replacing QuickStatsCard, layout switch + remove PersonalContextCard wrapper, plus a conditional ConferenceAttendanceSection that queries upcoming/active conferences for the current user. Note: the conferences feature lives on feature/conferences right now — D's conference section depends on that branch landing in main first. Until then, D ships without the conference section (it's a conditional render so this is graceful).

What's not in any variant (deferred to brand-direction conversation)

  • Category-specific tints on QuickActionCards (would need secondary accent decision)
  • Display font for greeting heading (Q5 typography pairing)
  • Decorative pattern or texture in PersonalContextCard background (Q4/#10/#11 territory)
  • Generative gradient avatars in sidebar (Q7 — already deferred)
